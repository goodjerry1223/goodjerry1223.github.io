VLA的演化主线

个人认为ACT、Diffusion Policy等任务型策略向VLA发展的主要动机有两个：

  1. 引入预训练VLM所具备的视觉和语义先验，使策略不必完全依赖机器人数据从零学习物体、场景和任务概念，从而提升跨物体、跨场景和跨任务泛化能力。

  2. 为多任务策略提供统一的任务定义入口。仅根据当前视觉状态，策略往往无法判断用户希望执行哪项任务；语言指令可以描述目标对象、操作方式和期望结果，从而消除任务歧义，并从多种可能行为中选择当前任务。

而相比OpenVLA等自回归的VLA模型将每个动作维度离散化为动作token，并自回归地逐个预测，duffusion、flow-matching等结构在连续动作表示、动作序列并行建模和多模态分布建模方面有明显优势，并且可以一次处理完整的action chunk。它们更适合表示高精度、平滑且可能具有多种合理解的机器人动作。

也就是说在现在常见的VLM+flow-matching的架构中，我们希望VLM具有对场景、任务的泛化理解能力，为flow-matching阶段提供足够的信息如包含场景、对象、任务和机器人状态信息的上下文表征，子任务拆解等。希望action expert在实时性方面实现动作的连续生成。

训练过程

一条训练样本包含：

图像 I
语言指令 l
机器人状态 q
真实动作序列 a

真实动作序列为：

a ∈ ℝ^(B×H×A) 例：batch_size 8 * action_size32 * chunk_size50

每次训练重新采样高斯噪声和时间：

ε ~ N(0, I)，t ~ Beta(1.5, 1)

OpenPI 代码采用“t=1 是噪声、t=0 是真实动作”的约定：

x_t = tε + (1 - t)a

训练目标为：

u_t = ε - a（速度场）

此时送入网络的是中间状态 x_t，不是始终相同的纯噪声。

图像token

每个视角分别处理：

224×224 RGB图像
→ patch_size 14×14 每个patch大小为14*14像素
→ 16×16=256个Patch
→ SigLIP
→ PaliGemma视觉投影
→ 256个2048维视觉token

文本token

PaliGemma Tokenizer

VLM Prefix P=图像token+文本token = 256M+L(M是相机路数，L是文本token长度) PaliGemma长度是2048维

Prefix内部使用双向注意力，因此所有有效图像和语言token可以相互读取。

动作token

Action_Expert A = Robot State + Action(经过时间步t拼接后的action) = 1+H Action_expert长度是1024维

网络中的逻辑序列为：

[Image Tokens][Language Tokens][State Token][Action Tokens]
└────── VLM Expert ──────┘ └──── Action Expert ────┘

注意力关系如下：

  • 整个noisy action chunk在当前flow step中是同时已知的，可以并行更新全部动作。

Dual-Expert Transformer内部计算

两套expert将token投影到兼容的attention空间：

8个Attention Head
每个Head维度256

随后将两部分的K/V按token维拼接，使action query能够读取VLM prefix：

PaliGemma K/V ─┐
               ├→ Masked Joint Attention → Action Hidden
Action K/V ────┘

注意力结束后，再将结果按token位置拆开：

  • Prefix结果回到2048维，由VLM expert继续处理；

  • Suffix结果回到1024维，由action expert继续处理。

这个过程重复18层。

输出与损失

取最后H个action位置的hidden states，

经过输出投影：

v_θ(x_t, o, t) = W_out Z_action ∈ ℝ^(B×H×A)

它预测的不是最终动作，而是 flow vector field

训练损失为：

L = ‖ v_θ(x_t, o, t) - (ε - a) ‖²（预测的速度场和真实的速度场）

梯度从 action 输出经过联合 attention 传递到 action expert，也能影响 PaliGemma 的机器人任务表征。

推理过程

按照当前观测构造VLM Prefix

动作推理从纯高斯噪声开始

用每一步的[robot state+action(time embedded)]的action token作为query

得到速度场 v_t = v_θ(x_t, o, t)

更新动作 x_(t+Δt) = x_t + Δt · v_t

最终得到action chunk 输出机器人动作

原始轨迹首先被统一成相同格式

Bridge 有一个很重要的处理：前 6 维动作被重新定义为

next_state[:6] - current_state[:6]

也就是说，模型学习的是相邻时刻的末端位姿增量，而不是使用原始控制命令。第七维夹爪始终当作连续值去学习最后化为0、1二值

action 和 proprio 归一化

代码在 data_utils.py (line 250)。

当前采用 BOUNDS，使用数据集的 1% 和 99% 分位数映射到 [-1,1]：

x_norm = clip( 2·(x - p01)/(p99 - p01) - 1, -1, 1 ) 确保数据归一到[-1,1]的范围中

注意两个细节：

  • proprio 的所有维度都会归一化。

  • action 最后一维 gripper 不归一化，仍然保持 0/1。

从轨迹构造动作 chunk

这是数据构造过程中最关键的一步，代码在 traj_transforms.py（第 12 行）。

对于轨迹：

a0, a1, a2, a3, a4, ...

当 action_horizon=4 时，每个时刻对应：

t=0 -> [a0, a1, a2, a3]
t=1 -> [a1, a2, a3, a4]
t=2 -> [a2, a3, a4, a5]

随后再增加 observation history 轴，因此最终是：

[traj_len, window_size, action_horizon, action_dim]

当前 window_size=1，所以单个 batch 中是 [B,1,4,7]。

图像、文字和状态进入模型前的处理

训练入口在 train.py（第 272 行）。

这里完成：

images = batch["observation"]["image_primary"]
proprios = batch["observation"]["proprio"]
actions = batch["action"].squeeze(1)
texts = ...

图像从：

[B, 1, H, W, 3]

变成：

[B, 3, H, W]

然后交给 VLAProcessor做两件事。

1.图像从 [0,255] 变换到 [-1,1]：

image / 255
(image - 0.5) / 0.5

2.在语言前加入 256 个 <image> 占位 token：

<image> × 256 + <bos> + instruction + "\n" + padding

最终 input_ids 固定为 [B,276]。 20 个文本 token实际上还要包含 BOS(序列开始标志符) 和换行等 token。

Camera images → SigLIP patch embeddings

图像配置为：

224×224
patch_size = 14

即得到 256 个 patch。

具体 patch embedding 是一个：

Conv2d(
    in_channels=3,
    out_channels=1152,
    kernel_size=14,
    stride=14
)

完整形状变化：

[B,3,224,224]
        ↓ patch Conv
[B,256,1152]
        ↓ 27 层 SigLIP
[B,256,1152]
        ↓ projector
[B,256,2048]

随后，256 个图像向量会替换 input_ids 中 256 个 <image> 占位符；真正的文字 token 使用 Gemma embedding。代码在所以图文分支最终是：

[B,276,2048]

给动作加噪，并加入 flow timestep

令真实动作 chunk 为：

x_1 ∈ ℝ^(B×4×7)

先采样同形状高斯噪声：

x_0 ~ N(0, I)

然后构造时刻 t 的 noisy action：

ψ_t(x_0, x_1) = [1 - (1 - σ_min)t] x_0 + t x_1

当：

  • t = 0：完全是高斯噪声 x_0

  • t = 1：约等于真实动作 x_1，还残留很小的 σ_min x_0（小的误差避免去噪中flow-matching方差为0）

时间 t 默认不是均匀采样，而是：

z ~ Beta(1.5, 1)
t = (1 - sigma_min) * (1 - z)

这会让训练更偏向较小的 t，也就是更嘈杂、更困难的区域。

时间通过正弦编码变为向量

三个 token block 怎样组成联合序列

完整逻辑序列是：

[ image + text 固定 276 个槽位 ]
[ proprio 1 token ]
[ action 4 tokens ]

总长度：

\[ 276+1+4=281 \]

但它们不是直接送进一个普通 Gemma。三个分支保留各自的参数：

VLM expert:
    hidden=2048, intermediate=16384

Proprio/Action expert:
    hidden=1024, intermediate=4096

action expert 是 18 层、1024 hidden 的约 300M Gemma 变体

完整过程是：

noisy action + 时间 t
        ↓ ActionEncoder
action token embedding
        ↓ 18层缩小版 Gemma Transformer
action hidden states
        ↓ ActionDecoder
预测速度 vθ
        ↓ Flow matching loss
与真实速度比较

Block-wise attention mask 是架构的核心

mask的可见性为：

因此：

  1. 图文不会被状态和动作反向污染。

  2. 状态可以结合视觉和语言形成条件表示。

  3. 动作可以读取所有条件。

  4. 4 个 action token 可以互相注意，因此整段动作是联合生成的，而不是逐动作生成。

位置编号也分块：

VLM:       1 ... 276
proprio:   1
action:    2, 3, 4, 5

proprio 与 action 共享 expert，因此状态位置为 1、动作从 2 开始，使它们在共享 RoPE 坐标系中形成连续序列。

VLM和action expert分支究竟如何交互

每一层中：

VLM hidden       → VLM 自己的 Q/K/V 投影
Proprio hidden   → action expert 的 Q/K/V 投影
Action hidden    → action expert 的 Q/K/V 投影

虽然 VLM hidden 是 2048、action hidden 是 1024，但二者都被投影成相同的 attention head 结构：

Q: 8 heads × 256
K/V: 1 head × 256

因此可以沿 token 维拼接：

query_states = torch.cat(...)
key_states   = torch.cat(...)
value_states = torch.cat(...)

然后只进行一次全局 attention：

softmax( QKᵀ / √256 + mask ) V

输出再按 token 长度拆回：

VLM output
proprio output
action output

然后各自经过自己的 o_proj、残差、RMSNorm 和 MLP。

所以这里不是带 router 的传统稀疏 MoE。更准确地说是：

参数独立的多个 Transformer expert，在每层 attention 中交换信息

Action Expert 预测速度场

action expert 最终输出：

[B,4,1024]

经过线性 decoder：

v_psi = self.action_decoder(action_embeds)

得到：

[B,4,7]

它表示 flow velocity。

真实目标速度是插值路径对时间的导数：

dψ_t/dt = x_1 - (1 - σ_min) x_0

训练损失为：

L = E[ ‖ v_θ(ψ_t, t, condition) - (x_1 - (1 - σ_min)x_0) ‖₂² ]

这里没有 action token 的交叉熵，也没有动作离散化；这是纯连续 flow matching。

推理时如何从噪声得到动作

首先，图像、文字、状态只计算一次：

VLM + proprio forward
→ 保存每一层的 K/V cache

然后初始化动作：

action = torch.randn(B, 4, 7)
t = 0
dt = 1 / 10

接着进行 10 次 Euler 积分：

for _ in range(10):
    velocity = model(action, t, cached_condition)
    action = action + 0.1 * velocity
    t = t + 0.1

即：

a_(k+1) = a_k + Δt · v_θ(a_k, t_k | condition)

注意这 10 次循环只运行 action expert；PaliGemma 的 K/V 被缓存，不会重复运行。这正是图中“multimodal prefix tokens → K/V”的实际含义。

最后动作被 clip 到 [-1,1]。

模型输出如何在仿真中变成机器人动作

先对action expert输出进行反归一化 得到最终7D pose

处理顺序是：

预测动作 [4,7]
    ↓ 前 6 维按 p01/p99 反归一化
位移增量 + 欧拉角增量 + gripper
    ↓ 欧拉角转 axis-angle
SimplerEnv 需要的 7 维控制命令

gripper 没有反归一化，因为训练时它原本就保留为 0/1，随后再根据 Bridge/Fractal 的约定转为环境中的开合命令。

第一步：末端增量转目标位姿。 仿真环境首先根据当前末端位姿（EE Pose），将预测的位移与旋转增量转换成绝对目标位姿。其中平移需要考虑参考坐标系，旋转需要通过旋转矩阵或四元数进行组合。

第二步：目标末端位姿转关节目标。 通过逆运动学（IK）求解满足目标末端位姿的关节角度：

q_target = IK(T_target, q_current)

在 RoboTwin 的 EE 控制模式中，cuRobo 进一步结合碰撞约束和运动规划，生成连续的目标关节位置、速度轨迹 q_d(t), q̇_d(t)。

第三步：目标关节位置转驱动力矩。 SAPIEN Joint Drive 接收目标关节位置和速度，根据 PD 控制规律产生驱动作用：

τ_PD = K_p(q_d - q) + K_d(q̇_d - q̇)

其中 q_d, q 分别为目标和实际关节位置，K_p, K_d 为位置刚度与速度阻尼。RoboTwin 还通过 compute_passive_force() 计算重力及科里奥利、离心效应补偿。

第四步：物理仿真执行。 PhysX 根据关节驱动作用、刚体动力学、关节约束及物体接触和摩擦，计算机械臂实际运动，更新 qpos、qvel 和末端位姿。

因此，π₀.₅ 输出的是运动目标，而非关节力矩；IK / cuRobo 负责将末端目标转换为关节目标，SAPIEN Joint Drive 负责关节驱动，PhysX 负责动力学与碰撞仿真。

在多步动作执行过程中，仿真器依次执行 Action Chunk 中的动作，并按照部署策略重新获取观测、调用 VLA 推理，形成闭环控制。

pi0.5的控制频率以及仿真执行

π₀.₅ 通过 Action Chunking 实现低频视觉推理和高频动作控制。模型通常一次预测未来 50 步动作，Flow Matching 采用 10 次积分，完成后将整个动作序列交给仿真环境执行。

在 RoboTwin 原生配置中，SAPIEN 物理仿真步长为 0.004s，对应 250Hz；默认每 15 个物理步采集一次示教数据，数据频率约为 16.67Hz。采用 pi0_step=50 的完整动作块执行方式时，每次推理生成的 50 步动作覆盖约 3 秒仿真时间，随后重新获取相机图像和机器人状态进行下一轮推理，因此按仿真时间计算的视觉策略为3s接收一次image更新。

在使用 50Hz 控制的 RoboTwin2.0 论文实验中，同样的 50 步 Action Chunk 则覆盖 1 秒。如果执行完整 50 步，视觉策略更新频率为 1Hz；若只执行前 25 步，则更新频率为 2Hz。

从实际计算耗时来看，已有 RoboTwin2.0 实验报告 π₀.₅ 单次完整推理约为 101–121ms。这意味着 VLM 和 Action Expert 生成动作块所需的时间远短于完整动作块对应的执行时间。在常规同步仿真中，模型生成动作期间环境暂停推进，推理结束后再执行动作；而实际机器人部署可采用异步推理或 RTC，使下一次推理与旧动作块的执行重叠，从而避免控制停顿。
